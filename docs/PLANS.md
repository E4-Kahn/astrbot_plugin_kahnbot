## P1 检索性能优化

**问题**：`Retriever.search` 每次把全表向量从 BLOB 解成 Python list 再逐条算余弦，
1024 维下每条向量展开成 Python float 要 44 KB（float32 只有 4 KB）。

本机实测（1024 维、真实检索代码）：

| 记忆条数 | 单次检索 | 瞬时内存 |
|---|---|---|
| 1,000 | 107 ms | +44 MB |
| 5,000 | 545 ms | +220 MB |
| 10,000 | 1,100 ms | +440 MB |

拆解（1 万条）：读库 0.11 s、解包 0.34 s、算余弦 0.98 s。

**两种改法的区别**

- **numpy 矩阵缓存**：启动时把全表向量读成一个 `float32` 矩阵（N×1024）常驻内存，
  每次检索只做一次 `矩阵 @ 查询向量`，再对 top-N 算字面分。检索变成一次矩阵乘法，
  但内存按 4 KB/条常驻（1 万条 39 MB、2 万条 78 MB），且新增/删除记忆时要维护矩阵（增量改一行）。
- **字面预过滤**：先用分词命中数给全表打一遍字面分（纯字符串操作，不碰向量），
  取前 200 条再解包算余弦。几乎不吃内存，也不用维护缓存，
  但每次仍要线性扫全表文本（1 万条约 50 ms），条数再翻十倍会变慢。

实测对照（1 万条）：

| 方案 | 耗时 | 常驻内存 |
|---|---|---|
| 现状 | 1,100 ms | 440 MB 峰值 |
| numpy 矩阵 | ~2.3 ms | 39 MB |
| 字面预过滤 | ~55 ms | ~0 |

**建议**：numpy 矩阵为主（AstrBot 环境自带 numpy，不算新增依赖），缺失时退回预过滤。
两者共用同一个打分函数，只是候选集来源不同。

**待定**：是否值得为 2 万条以上的记忆做分库/分表（目前看不需要）。

## P2 `[沉默]`

**动机**：真实聊天里不是每句都要回。对方只是"嗯""好""晚安"收尾时，再接一句反而假。

**不要用"想不想"这种措辞**——模型没有意愿，只有判断规则。实测（deepseek-v4.1-flash，
16 个场景各一次调用）：把规则写成"谁先开口 + 这句是不是收尾"后 14/16 符合预期；
写成"不想接就不回"时，连"主人先道晚安"都会沉默（因为把"晚安"本身当成收尾）。

**建议的规则**（写进提示）：

> 判断要不要回，只看谁先开口、这句是不是在收尾：
> - 上一句是你说的，对方只是在回应你（你道晚安他回晚安、你叮嘱完他回"嗯/好/知道了"）→ 不回；
> - 对方先开口（哪怕只是"晚安"）、在问你、开新话题、撒娇、夸你 → 回。

**但不要只靠模型**。程序侧再做一层确定性判定，作为硬规则先跑：

- 条件：`她说了最后一句` 且 `当前消息是收尾词`（嗯/好/好的/晚安/知道了/行/OK/睡了…，长度 ≤6）
  → 直接沉默，不进模型（省钱、零误判）；
- 模型输出的 `[沉默]` 只用来兜住"收尾词判断不了"的边缘情况；
- 连续沉默上限（默认 1），超了强制回一句；私聊是否允许沉默可配置（默认允许）。
- 沉默不计入唤醒配额，但记流水；把这条塞进 `unanswered`，下次开口自然接上。

**待定**：收尾词表要包含哪些（"哦""嗯嗯""行吧"算不算）；是否允许在私聊沉默。

## P3 人物小档案

**动机**：现在记忆是"一条条事实"，缺"对某个人的整体印象"。注入时也更容易写成一句人话。

**方案**

1. 新表 `profile(person_id, name, relation, note, style, updated_ts, dirty_ts)`，不动 `fact_index`。
2. `note` ≤120 字、第三人称（"他是主人的同事，最近在准备考试，喜欢喝冰美式"）。
3. 生成：挂在现有 6 小时汇总里，只处理"脏了的人"（新流水 >N 条或超过 3 天），
   输入旧档案 + 最近消息，输出合并后的新档案；多人可合并进一次调用。
4. 注入：按对话对象注入 `<profile>` 块（≤120 字）。主人有自己的档案；
   群友档案只从该群的话里长，不跨群、不带私聊内容。
5. `style`：她自己养成的说法（≤3 条 × 30 字），汇总时一起更新。

**成本**：每人每 3 天最多一次，约 300–600 tokens，可批量。

**待定**：档案和 `fact_index` 的关系（档案里提到的细节要不要同时留成事实）；档案是否也给群友看。

## P4 表情包

**方案分两档**

- QQ 内置表情：`mface` 组件，零素材成本，只需要模型输出表情名/ID。
- 图片表情：本地表情库 + 语义标签，模型输出 `<sticker:名字>`，插件负责找文件发送。

**风险**：刷屏、版权、审核。建议先做"被逗笑/撒娇时小概率跟一条"，且不进流水。

**待定**：素材从哪来；要不要做表情库管理指令。

## 记忆归档规则（常被问）

**归档 ≠ 删除**。归档是把一条记忆标成"旧了、默认不参与检索"，文件和数据库里都还在，
`/kahn memory facts` 能看到（带〔已归档〕标记），需要时也能恢复。

触发条件（三个同时满足）：

1. 重要度 < 60（LLM 写入时打的 0–100 分）；
2. 30 天没被检索命中过（`last_hit_ts` 空则看创建时间）；
3. 没有待发提醒（`due_ts` 为空）。

为什么这么设计：重要度 ≥60 的（承诺、纪念日、关键偏好）永远不归档，只参与时间衰减；
低重要度又长期没人提的（"今天吃了麻辣烫"）才收起来，避免检索被噪音淹没。

时间线示例：

- 11-12 记下"主人喜欢冰美式"（重要度 70）→ 永远不归档；
- 11-12 记下"今天外卖点了麻辣烫"（重要度 20）→ 12-12 之后若一次都没被检索到，进归档；
- "下周三体检"（重要度 80，带 `due_ts`）→ 提醒发完 `due_ts` 清空，但重要度 80 仍不归档。
